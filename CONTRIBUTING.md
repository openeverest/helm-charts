# Contributing to OpenEverest Helm Charts

Thank you for contributing! This guide walks you through making changes to the chart and publishing a release.

## Branches

| Branch | Chart for | Target it for |
| --- | --- | --- |
| `main` | OpenEverest v2 (Developer Preview) | New features and fixes |
| `v1.x` | OpenEverest v1 (current release) | Fixes for the 1.x line |

On 18 August 2026 the two lines swapped branches: v2 moved from `v2` to `main`,
and v1 moved to `v1.x`. Both lines are still developed; only the branch names
changed. The
[v1 lifecycle](https://openeverest.io/blog/v2-developer-preview-release/#timeline)
is unchanged.

The `gh-pages` branch is generated by the release workflow and is not edited
directly.

### If you cloned or forked before 18 August 2026

Your `main` still holds the v1 chart, so a branch cut from it changes the wrong
one. A local `main` reporting a large `ahead N, behind M` is v1 tracking v2 —
do not `git pull` it.

Forks were not renamed. If you only work on v2, re-fork or press **Sync fork**
and choose *Discard commits*. To keep working on v1 as well, rename `main` to
`v1.x` in your fork's branch settings first, then repoint your clone.

Pushing directly to this repository — rename `main` first to free the name:

```sh
git fetch origin --prune
git branch -m main v1.x
git branch -u origin/v1.x v1.x
git branch -m v2 main       # skip if you never had it
git branch -u origin/main main
git remote set-head origin -a
```

The [core repository](https://github.com/openeverest/openeverest/blob/main/CONTRIBUTING.md#which-branch-to-target)
moved the same way, with `release-2.0` in place of `v2`; its contributing guide
has the full fork walkthrough.

## Prerequisites

The following tools must be available in your `PATH`:

| Tool | Purpose |
|---|---|
| [`helm`](https://helm.sh/docs/intro/install/) ≥ 3.x | Packaging and dependency management |
| [`yq`](https://github.com/mikefarah/yq) ≥ 4.x | YAML patching in `prepare-chart` |
| [`docker`](https://docs.docker.com/get-docker/) | Running `helm-docs` for doc generation |
| [`git`](https://git-scm.com/) | Worktree-based `gh-pages` publishing |
| [`go`](https://go.dev/doc/install) (the version in `tools/bundled-compat-check/go.mod`) | Checking the bundled extensions before `publish` |

All `make` targets must be run from the `charts/everest/` directory:

```bash
cd charts/everest
```

```
helm-charts/
├── charts/
│   └── everest/                    ← main chart directory (work here)
│       ├── Makefile                ← all automation lives here
│       ├── Chart.yaml              ← chart name: openeverest, version & dependencies

```

## Making Changes

### 1. Fork & clone

```bash
git clone https://github.com/openeverest/helm-charts.git
cd helm-charts
git checkout -b my-feature
```

### 2. Install dependencies

```bash
cd charts/everest
make deps
```

This adds the required Helm repos (`prometheus-community`, `victoriametrics`, `percona`, `percona-olm`) and runs `helm dependency update` for all sub-charts.

### 3. Edit the chart

Make your changes under `charts/everest/templates/`, `values.yaml`, or the relevant sub-chart.

### 4. Prepare your PR

Before opening a pull request, run:

```bash
make prepare-pr
```

This will:
- Re-run `helm dependency update` for all charts
- Regenerate `README.md` from `README.md.gotmpl` via `helm-docs`
- Re-sync the CRDs, the controller RBAC and the built-in BackupStorageClasses from [`openeverest/openeverest`](https://github.com/openeverest/openeverest) at `OPENEVEREST_CRD_VERSION`, `main` by default (see [Updating CRDs](#updating-crds) below)

Commit the resulting changes along with your feature work.

## Updating CRDs

If your change requires refreshing the CRDs from the [`openeverest/openeverest`](https://github.com/openeverest/openeverest) repository, run:

```bash
make crds-gen OPENEVEREST_CRD_VERSION=<branch-tag-or-commit>
make link-crds
```

- `OPENEVEREST_CRD_VERSION` defaults to `main`, the openeverest branch that carries v2. Pass a tag or a commit SHA to pin the sync to a release or to a reproducible point. `controller-manifests-gen` and `backupstorageclasses-gen` sync from the same ref.
- `crds-gen` fetches the CRDs from `config/crd` in `openeverest/openeverest` via `kustomize` (runs in Docker — no local `kustomize` install needed).
- `crds-gen` labels every CRD with `everest.percona.com/crd: "true"` and `openeverest.io/version` (= `VERSION`).
- `link-crds` updates the symlinks in the top-level `crds/` directory.

Commit the updated files in `charts/everest-crds/templates/` and `crds/`.

## Publishing a Release

> **Note:** Only maintainers with push access to `gh-pages` should do this step.

### Full release (bump version → publish)

```bash
make release-and-publish VERSION=1.2.3
```

This single command:
1. Labels the CRDs with `openeverest.io/version` (= `VERSION`)
2. Stamps `version` (= `CHART_VERSION`) and `appVersion` (= `VERSION`) in the `Chart.yaml` files (`openeverest`, `everest-crds`)
3. Updates image references in `values.yaml`
4. Re-pins dependency versions in `Chart.yaml`
5. Records in the `openeverest` `Chart.yaml` annotations the release (`openeverest.io/version` = `VERSION`) and the compatibility window that OpenEverest stamps on its CRDs (`openeverest.io/contract-version`, `openeverest.io/min-contract-version`, `openeverest.io/upgradable-from`). It fails when the CRDs disagree, and only warns when they carry no window
6. Runs `helm dependency update`
7. Checks every extension the chart bundles from an OCI registry (such as `plugin-hub`, at the version locked in `Chart.lock`) against that window, and refuses to package the chart when one was built for an OpenEverest outside it (`make check-bundled-compat`). An extension that declares no OpenEverest version only gets a warning, and a chart without a window is not checked
8. Packages the chart into a `openeverest-<CHART_VERSION>.tgz`
9. Regenerates `index.yaml` on the `gh-pages` branch (preserving prior releases)
10. Commits and pushes `gh-pages`

After pushing, the chart is available within minutes:

```bash
helm repo add openeverest https://openeverest.github.io/helm-charts/
helm repo update
helm search repo openeverest/openeverest
```

### Step-by-step (if you need to separate the release from the publish)

```bash
# 1. Bump versions and update dependencies
make release VERSION=1.2.3

# 2. Commit the version bump to main
git add -A
git commit -m "Release v1.2.3"
git push origin main

# 3. Publish packaged chart to gh-pages
make publish VERSION=1.2.3
```

### Chart-only bump (minor chart fixes without changing the app version)

When you need to fix something in the chart itself (e.g. a template bug, a label change) without bumping the application version, pass `CHART_VERSION` separately:

```bash
# Release chart 1.2.4 while keeping appVersion at 1.2.3
make release-and-publish VERSION=1.2.3 CHART_VERSION=1.2.4
```

When only `VERSION` is provided, `CHART_VERSION` defaults to the same value (backward-compatible behavior).

The *Everest Chart Release* workflow takes the same split: its optional `chart_version` input, and `branch` also accepts a release tag such as `openeverest-2.0.0-dev.4`.

### Bundled plugin-hub

The chart bundles plugin-hub at the version locked in `Chart.lock`; a release resolves `Chart.yaml`'s range again when it packages the chart.

- **`plugin-hub-bump`** runs daily, on demand, or on a `repository_dispatch` of type `plugin-hub-released`. It opens (or refreshes) a `chore(deps): bump plugin-hub to X` PR on the `ci/bump-plugin-hub` branch, saying whether merging it cuts a release. It uses the `ROBOT_TOKEN` secret when present, so that the PR's CI runs.
- **`plugin-hub-release`** runs when `Chart.lock` changes on `main`. If plugin-hub's chart changed beyond its image since the plugin-hub in the latest release on the line, it dispatches a chart-only patch release built from that release's tag: `2.0.0-dev.4` becomes `2.0.0-dev.4.1`, with the same OpenEverest. Image-only plugin-hub releases cut nothing: plugin-hub updates its own image in place. On a stable line it only warns: pick that `chart_version` by hand. Run it by hand with `dry_run` to see what it would release.

### Dev / pre-release

For a dev release using `-dev` image variants and telemetry disabled:

```bash
make release-dev VERSION=1.2.3-dev
```

This does **not** call `publish` — dev builds are not pushed to the public Helm index.

## Available `make` Targets (summary)

| Target | Description |
|---|---|
| `make deps` | Add Helm repos and update all dependencies |
| `make prepare-pr` | Sync deps, regenerate docs, refresh CRDs — run before opening a PR |
| `make release VERSION=x.y.z` | Bump all versions and update images/deps |
| `make release VERSION=x.y.z CHART_VERSION=x.y.z+1` | Bump chart version independently of app version |
| `make publish VERSION=x.y.z` | Package chart and push to `gh-pages` |
| `make release-and-publish VERSION=x.y.z` | `release` + `publish` in one step |
| `make release-dev VERSION=x.y.z` | Dev release with `-dev` images, telemetry off |
| `make annotate-chart VERSION=x.y.z` | Record the release and the CRDs' compatibility window in `Chart.yaml` annotations (part of `release`) |
| `make check-bundled-compat` | Refuse a chart that bundles an extension outside the compatibility window in its `Chart.yaml` (part of `publish`; CI runs it on every pull request and before every release) |
| `make crds-gen OPENEVEREST_CRD_VERSION=<ref>` | Regenerate CRD templates from `openeverest/openeverest` (default ref `main`) |
| `make link-crds` | Refresh symlinks in `crds/` from CRD templates |
| `make docs-gen` | Regenerate `README.md` via `helm-docs` (requires Docker) |
